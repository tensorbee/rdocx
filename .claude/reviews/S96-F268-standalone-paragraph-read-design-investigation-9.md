## Certificate, synchronization and lifetime

Store one positive certificate containing the complete standalone XML key and Weak<BodyContent> for the exact immutable staged Arc that matched the actual reader output. No second CT_P/CT_Document, Source receipt, error or record history is stored. Key bytes are additional retained XML storage and must be reported as such. Weak ownership retains allocation metadata, not a live AST payload.

A lazy OnceLock containing an Arc<Mutex<Option<certificate>>> is a viable finite container. It avoids allocating a mutex/key for every opening block, ineligible paragraph or failed read. Existing Arc<BodyBlockScan> clones share an initialized cell. fresh_context_piece_from at Native document.rs:9428may carry that initialized cell only while it preserves the same staged model Arc at9433. New byte/model construction starts without a certificate. A changed model identity must refuse an old certificate even if its bytes or value appear equal. Do not add an opening scan or eagerly parse/cache paragraphs.

On lookup, a hit requires the complete key to match and the certificate's Weak model identity to match this candidate's current staged Arc. None, expired Weak, changed key, different Arc, unknown/private candidate or wrong reader route cannot hit. Keep a strong candidate Arc only for the duration of this read. Release all memo/certificate locks before parsing, complete CT_P equality, cloning the returned paragraph or invoking any caller logic.

On a miss, execute CT_P::from_xml_fragment once and propagate its exact error. Do not run a reduced validator first, swallow a resource error or retry under another reader. On actual success, qualify both values and compare the complete CT_P. If they qualify and match, replace the sole positive key/model certificate. If they do not, return the actual reader result and clear the old positive entry for this attempted successful replacement. A reader error is never cached and need not destroy an unrelated prior positive key. Concurrent successful misses may replace each other's one entry, but must never form a list or suppress either actual read. Wrong keys must not permanently starve a later stable key as a one-shot negative OnceLock would.

On a hit, preserve CommentAnchorRead's owned CT_P tuple by cloning the proven paragraph outside locks. A borrowed-lifetime tuple or new paragraph representation is unnecessary. The new copy is real work, not eliminated allocation. No source/flow metadata is taken from the certificate.

Current staged model Arcs are immutable value storage at Native document.rs:9022. No production staged-model Arc::get_mut/strong-count authority branch was found in the Native/binding consumers. A new Weak nevertheless changes uniqueness behavior and must be tested. Arc::make_mut on a staged value must dissociate the old Weak or create a new identity before mutation. BodyBlockScan mutation/replacement must not allow a certificate for an old model to become positive for a new one. Copy-on-write of the outer writer vector from cold design8is independent of this model certificate. Existing Part-child proved/canonical/namespace OnceLocks remain separate and unmodified.

At most one key exists per live shared certificate cell. Repeated scope changes replace it. Current records and user-held snapshots may retain their existing immutable blocks, but the cache must not add a chain of old blocks/models or retain old keys after replacement. Retained key length/capacity, certificate/container counts, actual key copies and returned model copies need separate observation. One complete key per block can still add substantial memory because namespace closure repeats declarations. This is not a zero-memory change and does not discharge the final memory rider.

## Advisory ordinal clarification after the actual candidate probe

The actual old candidate-only diagnostic in `.claude/scratch/S96-final-evidence/f268-opening-model-proof-implementation-20261107-1/old-diagnostic/candidate-only/OBSERVATION.json` completes four original0/1/2reply sequences, with12successful actions and reopen checks. The100case has103paragraph candidates,10complete equalities,85finite candidates and158finite actual reads. These are diagnostic observations, not shipping acceptance. They confirm that direct use of the story-item index is an ineffective hint for this fixture and do not weaken the standalone equality requirement.

A once-per-CommentAnchorRead-factory advisory paragraph-ordinal snapshot is sound as immutable value storage. Under the existing offered-record selection and mutex, walk the selected staged block vector once and retain the block/model Arcs whose staged variant is Paragraph. Do not deep-clone a model or writer record. Release the mutex before the source paragraph loop and every actual reader, qualification, comparison, clone or callback. This costs one bounded O(N) snapshot per factory, not one scan or record clone per paragraph and not necessarily one snapshot per entire reply.

The source ordinal advances for every actual main-part Body owner0, non-end Paragraph with a one-component location, including an ineligible paragraph or missing candidate. It must not advance only for finite, equal or cacheable paragraphs. Related-story, cell, control and nested paragraph locations do not consume that direct-main-body ordinal. Native document.rs:12798still defines source indices through the item inventory, while BodyBlockScan.staged at9022provides only immutable value storage. The ordinal snapshot does not close that physical mapping distinction. Missing staged entries, extra preserved nodes, transparent wrappers or other mismatches may shift hints. They remain misses unless the exact same-reader finite value proof independently succeeds.

Both-side finite qualification must precede the optional complete CT_P comparison. This matters after design8's clarification: Field equality can transitively read revision XML through cached_result_runs, so an unconditional advisory equality on private data would add actual reader work that the original parent-read call did not perform. The diagnostic may observe such comparisons, but production cannot inherit that diagnostic order. On a noneligible candidate or returned paragraph, simply keep the successful actual standalone reader result without the additional comparison or certificate. Wrong eligible candidates can only fail equality or certify the same complete eligible value for the exact XML key. They cannot certify a location, source span, Part read or input role.

Only a prior successful actual fixed standalone read plus eligible complete equality may populate the positive certificate. Future hits still require complete XML-key equality and identity with the candidate's current immutable staged Arc. A different ordinal or record cannot make another Arc inherit a proof. The snapshot's strong model/block references are call-local and must drop with the factory. The retained certificate remains one key plus Weak identity, with no additional AST or history. Existing force-off, missing-stage and source-only fallbacks remain. Selecting a fallback record by serialized-first ordering does not itself create read authority.

The fixed reader-policy, error-order and private/Weak rules above are unchanged. Snapshotting is optional metadata preparation and must not move ownership checks, source discovery, namespace restoration or comment-marker scanning later. A certificate mutex failure must conservatively use the actual reader rather than introduce a new user-visible parser error. Validate sole-strong-owner plus Weak copy-on-write, changed model identity, reordered/missing hints and unrelated malformed paragraphs while other entries are warm. Required diagnostic observation still includes exact key/model persistence through the actual first, second and third reply actions. No corrected-ordinal hit rate, cache implementation, elapsed improvement or adoption is asserted by this clarification.

Keep the concrete snapshot and certificate operation in the existing Native policy owner. If a crate-private named hint value is needed across the comments/document module boundary, it must own the substantive snapshot/read-certificate invariant and retain private fields. Do not introduce a forwarding-only collection wrapper, expose BodyBlockScan fields, add a generic callback provider or duplicate reader/qualification policy in comments.rs. This is a clarification of investigation9, not a new design pass or implementation permission.
