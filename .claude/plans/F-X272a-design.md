### 3.2 Private raw discrimination across the real crate boundary
`crates/rdocx-oxml` is a separate crate, so a `pub(crate)` item there is invisible to `crates/rdocx`. V10 keeps the policy in `rdocx` and adds no item to `rdocx-oxml`. `NoteType::from_str` maps `""`, `normal` and every unknown to `Normal`, so a presence bit cannot separate the three.

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
pub(crate) enum RawNoteType {
    Omitted, Empty, ExplicitNormal, Separator,
    ContinuationSeparator, ContinuationNotice, Unknown,

```

`raw_note_type_in_scope(owner_xml, bindings)` resolves every attribute prefix through `bindings` and accepts `type` only when its prefix maps to `W_NS`. No colon means no namespace, and an unbound or foreign prefix means Omitted. Exact `normal` is ExplicitNormal, empty is Empty, the three specials are their own variants, anything else is Unknown. `raw_note_type_in_part` computes part-root bindings and reads raw `w:id` in scope. `normal_note_owner` returns true for `Omitted` and `ExplicitNormal` only. `preflight_note_identities` refuses atomically on a changed owner or reference that is `Empty` or `Unknown`. `verify_custody_reference_identity` checks resolved units only.

In the comparison layer, when either paired owner is `Empty` or `Unknown`, the owner bytes must be identical in original and edited and the paired reference identity must be unchanged. If either differs, the comparison refuses before mutation. This covers content changes, not only attribute changes, and does not change the parser model or public note type.

### 3.3 Reference-owner association
Build a reference inventory keyed by physical story part, aligned body owner path, run boundary and occurrence ordinal, targeting the normal owner with the matching id in the same input. A missing target refuses. A normal note with zero references is unused, and original unused notes are preserved. A new unused note is Q-A430-04. Pairing uses the actual reference owner: align owners, pair occurrences by ordinal up to the smaller count, treat an original-only reference as a deletion and an edited-only reference as an insertion, and refuse a moved or ambiguous reference unless the existing move contract carries it. Definition custody exists only when the definition itself is added or removed. For an `Empty` or `Unknown` owner, a changed reference refuses. If the reference and owner bytes are unchanged, the owner is preserved exactly.

A normal owner may have more than one reference in one input. All references to the same normal owner belong to one custody unit when that definition is added or removed. The reference inventory records every reference site by body owner path, run boundary and occurrence ordinal. The body bookmark pair is placed at the first reference site in document order. The unit's reference list contains every site. A selector that covers only one reference site of a multi-reference unit is partial and refuses under Section 4.

The resolved output's reference inventory for each normal owner equals the destination input's inventory for that owner. The library does not synthesize an additional reference. A Word-admitted input therefore cannot acquire a new shared reference through compare. A shared-reference input that is already unreadable in Word 16.114.1 may still be preserved as imported XML, but preservation is not a claim of Word compatibility. The controlled shared-reference native negative in Section 1 does not change this reference-owner contract.

### 3.4 Custody markers, transaction-local bits, persistent token
Generated custody uses two hidden, zero-width STANDARD Word bookmark pairs bound by the actual reference owner. The names carry the story's original and edited part-presence bits at the emitting transaction. The token in the names is persistent identity. At emit time it equals the shared comparison-local revision id. After Word normalization it may differ from every current revision id.

- Body `_rdocxCmpNoteF<token>P<o><e>B`: start then end adjacent, a direct child of the body paragraph, immediately before the reference run and outside the body revision wrapper. Native pending shows parent `p` at `/document/body/p`, with the body insertion at `/document/body/p/ins`.
- Note `_rdocxCmpNoteF<token>P<o><e>N`: start then end adjacent inside the note owner's first note paragraph. For an addition, the pair is emitted inside the `ins` content wrapper so Word's reject removes it with the rejected content. For a deletion, the pair is emitted at the direct boundary outside the `del` content wrapper so Word's reject keeps it while the definition is restored. The library resolver does not depend on that placement: it retires both of its own markers when the part settles. When a definition is unchanged, no note marker is emitted because there is no definition custody.
- `<token>` is one to nine ASCII digits, canonical without leading zeros except `0`. It is identity, never chronology or a current revision id.
- `<o>` and `<e>` are `0` or `1`. `o` is original input note-part presence at that transaction, `e` edited presence. `1` means one internal relationship of the matching type, the target part exists and its content type matches. `0` means absent.
- Maximum length is 27, below 40, and each pair is zero-width and hidden.

Both names carry the same bits and token. Units from different transactions may differ, which is provenance, not ambiguity. Disagreement on bits or token refuses. Association is by actual reference owner. Token mismatch, different owner, reference or bits, duplicate name or missing counterpart refuses, except retained tombstones and completed imported markers in Section 3.7. Pair id: start and end share one id from the existing allocator's used set, and an imported pair is valid only when its id appears exactly twice in the relevant part. Bookmark ids may be renumbered by Word or F-X280, so recognition never depends on id value. Native pending shows body bookmark id 0 and note bookmark id 4, and native accept renumbers the note bookmark to 1.

**Narrow allocator amendment.** `IdAllocator::new` starts `next` at zero (`comparison.rs:764`) and `allocate` takes the next unused id (`:815`), filling holes. A resolved unit's revision id disappears from the listing, so a later comparison could reuse it and give a new unit a token equal to a tombstone's token. The allocator's initial used set is extended by every custody token and every custody bookmark id in the compared parts. This reserves tokens and bookmark ids and changes no algorithm, id convention, story scope or history. Current revision ids are allocated normally and may be lower than older tokens. That is harmless because the token is identity, not chronology.

Imported marker is custody only when body and note names match the full grammar with valid bits and the same token, both pairs are adjacent with one start and one end, the body pair is a direct child of the body paragraph before a normal reference run, the note pair is a direct child of the note paragraph or of one revision wrapper that directly contains the note content, each name appears once, and the owner is normal. A structurally invalid name is an ordinary bookmark. A fully valid but cross-owner, mismatched-token, duplicate-name, mismatched-bit or missing-counterpart marker refuses, except resolved tombstones. A valid Word-normalized pending marker is not an ordinary bookmark and is not a resolved tombstone.

**Open bits, completed bits.** A custody unit's bits describe its own transaction. While that transaction is open, the bits vote in the part-presence predicate of Section 3.6. A pending addition from an absent part carries `0/1`, and after reopen the part exists because that addition is still pending. A later comparison that preserves it keeps the same open unit. The bits are not compared with current presence and are never rewritten. Once the part settles, the transaction is completed, its library markers are retired, and its bits no longer exist in the document. Collision rebinding: original names win, an edited collision with a different owner is rebound to a fresh token and fresh ids, bits do not change, and the same owner keeps original names and ids.

### 3.5 Custody units, revision grouping and listing
A custody unit is rediscovered from the two pairs: `body_name`, `note_name`, `family`, `direction`, `token`, `note_owner`, `references`, `bookmark_ids`, `original_present`, `edited_present`, and the current revision element ids read from the bound owners. It is not a custom part or public model. The token is persistent identity. The current revision ids are not compared to the token.

Two durable lifetimes are read from persisted bytes alone. There is no current-versus-prior class.

- **Open lifetime**: the part contains at least one pending unit, meaning a bound owner still carries a revision wrapper. Every custody unit in that part is open. A pending unit still has its wrappers. A resolved unit in the same part keeps its markers as a retained tombstone until the part settles. Every open unit's bits vote in the predicate in Section 3.6.
- **Completed lifetime**: the part contains no pending unit. Library-emitted markers were retired when the part settled, so any custody marker still present is an imported Word-resolved marker. It is preserved byte-for-byte when untouched, excluded from the predicate, and retired when the library edits the bound owner or part or adds custody to that part.

A unit emitted by the current comparison and the identical reopened unit have the same names, bits, token, wrappers and ids. They are the same open unit and resolve identically. Nothing in the resolver reads which session emitted the unit or how many comparisons have run.

The unit's revision elements are every body reference wrapper at every reference site plus the note content wrapper and the note paragraph-mark wrapper in the bound normal owner. A unit is pending when every body reference site still carries a revision wrapper containing its reference and the note owner still carries a revision wrapper around the definition content. If only some body sites carry wrappers while the note content wrapper is present, the unit is inconsistent and refuses. A unit is resolved when those wrappers are gone after accept, or when the reference and definition are gone after reject. The note bookmark is present exactly while the definition is retained.

`story_revisions` lists each modeled revision element separately. For the native pending fixture it returns three entries: body insertion id 1, note paragraph-mark insertion id 2 and note content insertion id 3. The token 7 is not necessarily a revision id and is not listed. Counts equal the number of revision elements. The public `StoryRevision` fields remain story, id, author, timestamp and kind. No token field, unit object or count collapse is added.

`accept_revision_id` and `reject_revision_id` select every revision element whose current `w:id` equals the argument (`revision.rs:297-304`, `:805-806`). Author and date select every element whose metadata matches (`:804`, `:807-811`). `accept_all` and `reject_all` select every element (`:803`). These callable semantics are unchanged. Section 4 states how those element selections group into custody units and when a partial selection refuses.

### 3.6 Part-presence and destination invariant
The library resolver restores destination package states. Accept goes to the edited input, reject goes to the original input. This is separate from the bytes Word retained in the synthetic probes. Word's retained markers and separator-only part are observations of Word output, not a product-policy waiver.

At settlement, let `U` be every open custody unit in the part: pending units plus retained tombstones. Let `N` be the number of retained normal note definitions physically present after the resolution removes definitions owned by resolved units. Let `R` be the number of retained unowned records that are neither normal definitions nor special records: owners whose raw type is `Empty` or `Unknown` including their children, direct part-root children that are not note owners, and retained owners that are neither normal nor one of the three special types. Let `base` be `0` if any unit in `U` has `o = 0`, else `1`. Let `E` be true if any unit in `U` has `e = 0`.

**Part-presence predicate.** The part is absent iff `N = 0` and `R = 0` and (`E` or `base = 0`). Otherwise it is present.

- `N > 0`: present, a retained normal definition needs the part.
- `N = 0`, `R > 0`: present, retained unowned invalid or opaque content needs the part.
- `N = 0`, `R = 0`, `E`: absent, an open unit's edited input had no part.
- `N = 0`, `R = 0`, not `E`, `base = 0`: absent, an open unit's original input had no part and nothing else needs it. Synthesized specials belong to that creation and are removed with it.
- `N = 0`, `R = 0`, not `E`, `base = 1`: present, original specials keep the part.

`N`, `R`, `base` and `E` are read only from persisted bytes and are unchanged by resolution order, reopen and token value. The predicate never reads a token as time and never asks which comparison emitted a unit. A completed transaction has no markers, so it does not enter `U`. An open transaction enters `U` and votes until the part settles.

When the part is absent under the predicate, remove it with its relationship, content type, own `.rels`, unshared targets, synthesized specials and every custody marker. This covers a rejected `0/1` creation and an accepted `1/0` deletion toward edited-absent. When the part is present, keep its retained normal definitions, imported specials and unowned content, and retire every open unit's markers at settlement. When `U` is empty and the existing part has no normal definition, no special and no unowned content, the comparison refuses atomically with a precise empty-part error rather than publishing an empty part.

An open unit's bits vote because its transaction is not closed. A completed transaction leaves no markers and does not vote. `R > 0` keeps the part regardless of `E`, so an accepted open deletion with `e = 0` does not delete untouched invalid or opaque content. This preserves N12 for both bit directions. No pruning, no reinterpretation of the invalid owner and no blanket refusal of otherwise supported unchanged input.

The only path that removes specials or unowned content is a part-absent settlement, whose corresponding original or edited input had no part. That is reject-to-original or accept-to-edited, not a silent prune. A prior open unit resolved in a later comparison has its bits in `U` until the part settles, so specials and unowned content are removed only when the predicate says the part is absent.

### 3.7 Tombstone grammar, imported Word-resolved markers and retirement
A resolved unit in an open part is a retained tombstone. Its body pair is present, and its note counterpart is present when the definition is retained and absent when the definition was removed. The retained tombstone keeps its markers because the part still contains at least one pending unit. When the part settles, library-emitted body and note markers are retired, restoring the destination state. A resolved library unit does not leave permanent markers. A reopened marker with no revision wrappers in a part with no pending unit is an imported completed unit, usually from Word resolving the revisions.

A body pair is custody when both names match `_rdocxCmpNoteF<token>P<o><e>B` with canonical token and valid bits, start and end share one id and are adjacent as a direct child of the body paragraph, and the token is not a live pending unit bound to a following reference owner in the same part. Its note counterpart decides definition retention. A body pair followed by a normal reference run inside a revision wrapper is pending, not resolved. An absent counterpart beside a live owner that still holds the definition refuses, and a present counterpart with a missing owner refuses.

**Pending, retained and imported, owner-local and id-independent.** A unit is pending iff every bound body reference site still carries a revision wrapper containing its reference and its bound note owner still carries a revision wrapper containing the definition content. If only some body sites carry wrappers while the note content wrapper is present, the unit refuses as inconsistent. The current wrapper ids are read from the owners. They are not compared to the token and are not required to be equal to each other. Word normalization can give the body insertion id 1 and the note insertions ids 2 and 3 while the token stays 7. That is pending, not a retained tombstone and not an ordinary bookmark. A token may also coincide with one or more current ids. That coincidence does not change recognition. If exactly one of the body reference wrapper and the note content wrapper is present while the reference and definition are both present, the unit refuses as inconsistent. A resolved unit has both wrappers absent after accept, or the reference and definition absent after reject. A resolved unit whose part still contains a pending unit is a retained tombstone. A resolved unit whose part contains no pending unit is completed, and any marker then present is imported.

**Imported Word-resolved markers.** A completed marker with a note counterpart and a live definition is an accept-state completed unit. A completed marker with an absent note counterpart, no reference and no definition is a reject-state completed unit. These markers are imported historical metadata in a settled part. They are preserved byte-for-byte when the bound owner and part are untouched by the current comparison. They are excluded from `U` and the predicate. When the current comparison edits the bound owner or part, including adding a new custody unit to that part, the library retires every imported completed marker in that part before emitting new custody. This retirement is mandatory on every comparison entry point that can add custody to a part, and it happens before any new marker is emitted. Retiring removes the library-owned marker pair and, if the predicate says the part is absent, applies the ordinary part cleanup. It does not rewrite user content. A malformed completed marker, such as a note counterpart present with a missing definition, refuses atomically rather than being reclassified as an ordinary bookmark. In a library-produced document, because a comparison that adds custody to a part retires its imported markers, a part with a pending unit never contains an imported marker. Admission of a foreign part that already contains a pending unit and a no-wrapper marker treats the marker as a retained tombstone, because wrapper presence is the only durable discriminator.

**Note placement.** The note pair is valid when it is a direct child of the note paragraph or a direct child of exactly one revision wrapper that is a direct child of the note paragraph and directly contains the note content. Native pending shows parent `ins` at `/footnotes/footnote/p/ins`. Native Accept All shows parent `p` at `/footnotes/footnote/p` after the wrapper is removed. A note pair inside an arbitrary nested wrapper, inside the paragraph-mark wrapper alone, or outside the bound note owner refuses. The body pair must remain a direct child of the body paragraph. Native pending shows parent `p` at `/document/body/p`, outside the body insertion. After any library resolution of the last pending unit in the part, the note marker is retired with the body marker at settlement. An imported completed note marker is preserved untouched when the owner is untouched and retired when the library edits the owner or part.

**Decodes.** Unit identity, bits `o` and `e`, persistent token, pending versus retained versus completed owner-locally and id-independently, definition retained versus removed, and owner and reference binding while the reference exists. **Cannot decode, and need not.** Direction after resolution, accepted versus rejected in general, chronology, and owner binding for an orphan completed marker whose reference was removed. Two body pairs with the same full name in one part refuse. Across parts names may repeat. A completed imported marker and an open unit sharing a token are distinguished by owner binding and wrapper presence, and the allocator reservation prevents a new unit from taking a completed unit's token.

### 3.9 Part-state policy and worked examples
A part is present when the main document has one internal relationship of the matching type and the target part exists with matching content type. Open units and retained tombstones enter `U`, and the predicate in Section 3.6 decides part presence. Completed transactions leave no markers and do not vote. Token value is never read as order.

| Original `o` | Edited `e` | Open unit | Accept effect | Reject effect |
|---|---|---|---|---|
| 0 | 0 | Absent, no unit | Absent | Absent |
| 0 | 1 | Created from edited bytes with exactly their existing special inventory | Definition retained, part decided by the predicate | Definition and reference removed, predicate can unwind the creation to absent |
| 1 | 0 | Deletion toward edited-absent | Definition and reference removed, predicate can remove the part | Definition restored, part present |
| 1 | 1 | Deletion toward separator-only, addition to special-only, or ordinary edit | Accept goes to the edited input: a deleted definition is removed, an added definition and reference are retained, specials retained, part present | Reject goes to the original input: a deleted definition is restored, an added definition and reference are removed, specials retained, part present |

A special-only part with the same special bytes plus new referenced normal notes is ordinary lifecycle, bits `1/1`, not refused. Original absent and edited present with only specials and no normal note has no custody unit, so no carrier persists the decision, and that case keeps the existing shell-count refusal at `comparison.rs:2357-2362`. Unexpected relationship multiplicity, missing target, wrong content type or duplicate internal relationship refuses before mutation.

**Example A, open `0/1` creation reject.** Original absent, edited present with a referenced normal note and synthesized specials. Reject removes the definition and reference. `U` has the unit, `N = 0`, `R = 0`, `base = 0`, so the part, relationship, content type, own `.rels`, unshared targets, synthesized specials and both markers are removed. A430-17.

**Example B, open `1/0` deletion accept.** Original present, edited absent. Accept removes the definition and reference. `N = 0`, `R = 0`, `E = true`, so the part, relationship, content type, imported specials and both markers are removed. A430-19.

**Example C, open `1/1` removal toward separator-only accept.** Original present with a normal note and specials, edited present with specials only. Accept removes the normal definition and reference. `N = 0`, `R = 0`, `E = false`, `base = 1`, so imported specials keep the part and both markers are retired at settlement. A430-20 and A430-35.

**Example D, open `0/1` creation accept.** Accept retains the normal definition, reference and synthesized specials. `N = 1`, so the part is present and both markers are retired at settlement. A430-17 companion.

**Example E, open `1/0` deletion plus untouched invalid definition, later unrelated comparison, accept old deletion.** The later comparison's units are empty for the old unit, which remains an open retained unit. The current document still holds the part with the untouched `Empty` definition. Accept removes the normal definition. `N = 0`, `R > 0`, so the part is present regardless of `E`, and the invalid definition is retained. A430-30 companion.

**Example F, open `0/1` addition plus untouched opaque content, later unrelated comparison, reject old addition.** The current document still holds the part with the opaque content. Reject removes the normal definition and reference. `N = 0`, `R > 0`, so the part is present and the opaque content remains. A430-31 companion.

**Example G, completed cycle with reopen.** Accept a `1/0` deletion to absent, reopen, accept a `0/1` addition, reopen, accept a `1/1` removal toward separator-only. Each transaction settles on its own, so its library-emitted markers are retired and no prior live revision or stale bit remains. The final `1/1` unit has `base = 1`, so the part remains separator-only. Completed provenance does not force the last part absent. A430-39.

**Example H, accept then edit the same retained normal note.** Accept an open `0/1` addition. The normal note remains and both markers are retired at settlement. Reopen and edit that note's text. The edit is an ordinary text edit with no custody, because no marker or prior live revision remains. A430-40.

**Example I, imported Word-resolved marker.** Word resolved a pending unit and left a body marker and possibly a note marker in a settled part. Reopen reads it as a completed imported unit. It is preserved byte-for-byte if the owner is untouched and does not enter `U`. If a later comparison edits that owner or adds custody to that part, the marker is retired before new custody. A430-41.

**Example J, native normalized pending fixture.** Token 7 names, body insertion id 1, note paragraph-mark insertion id 2, note content insertion id 3, note marker parent `ins`. Recognition is pending. Listing is three entries. Id selectors 1, 2 and 3 are partial and refuse. Token 7 selects no element in this fixture and leaves the unit pending. Author, date and all select all three when the metadata matches and fully resolve. The library accept keeps the definition and the reject removes the created part. A430-33 and A430-34.

**Example K, token coincidence.** A normalized unit has token 7 and current ids 7, 8 and 9. Public id 7 selects one element and is partial, so it refuses. It is not a no-op. A unit with token 7 and ids 1, 2 and 3 plus an unrelated revision id 7 makes id 7 select the unrelated revision, not the unit. The unit remains pending and the unrelated revision resolves normally. A430-42 and A430-43.

**Example L, mixed creation lifetime unwound.** Original absent, compare to note A, save and reopen with A pending `0/1`. Compare the reopened document to an input that retains A and adds B. B's unit is `1/1`. Reject A and B in either order with reopen between. After both, `U` has both resolved units, `N = 0`, `R = 0`, `base = 0` because A has `o = 0`, so the part, synthesized specials and every marker are removed. No leftover separator-only part remains. A430-44.

**Example M, byte-determined open lifetime.** Save a document with one open `0/1` unit, reopen it, and reject. The resolver reads the same names, bits, token, wrappers and ids it would have read before the save. `U` has the same unit, the predicate gives the same result, and no in-memory record or current-versus-prior class is consulted. A unit emitted by the current comparison and the identical reopened unit resolve identically. A430-45.

### 3.10 Ignored footnote story
When `footnote` is ignored, retain original part bytes, create no new definition and write no note-body revision. Body reference changes are still compared. After compare and each resolution every retained body reference must resolve to a normal owner. A retained reference with no owner refuses, and a reference to a note existing only in the ignored edited input refuses. A deleted reference leaving an original note unused is preserved. No dangling reference is published. Ignored open custody units are preserved byte for byte, no new custody is emitted, and a resolution that would change an ignored revision-bearing owner refuses. Untouched invalid and opaque content in the ignored part is preserved byte for byte. The later selected-reference probe shows Word can remove a selected reference and its normal definition while leaving an unrelated insertion pending and retaining only separator definitions. That is a narrow producer observation, not a library selector qualification.

### 3.11 Package cleanup, save and reopen
Definition removal drains the exact owner, removes only relationships it owns that no retained owner references, removes internal targets only when unshared, removes overrides only for removed parts, preserves remaining relationship ids and order, and reopens before publication. Part removal uses `remove_part`, `remove_override` and `remove_part_rels`, removes the internal main relationship while retaining every other relationship in original order and id, removes unshared targets and overrides, and reopens before publication. Refuse if sharing cannot be proven. Part creation uses `reserve_document_part_bundle`, existing producer declarations are never overwritten, and signatures are invalidated by any part, relationship or content-type change.

Save and reopen preserves both custody pairs and zero-width adjacency, bits, persistent tokens, current revision wrappers and ids, tracked revisions, every untouched imported note and special, every untouched invalid or opaque record, every open custody unit, every completed imported marker, selected part presence, and held-handle invalidation. Bits must agree within one unit before use, and raw types are recomputed, never persisted. Library-emitted markers are retired when their part settles, so a reopened settled document has no library custody markers. A comparison that adds custody to a part retires imported completed markers before emission, so a published open part contains no imported marker. Imported Word-resolved markers are preserved when untouched. Between selective operations, open units keep their markers until the part settles, and completed imported markers stay byte-for-byte. Reopen decodes the same open units and the same predicate without an in-memory record. No custom part, public field or persisted extension.

### 3.12 Atomicity, postconditions, endnote
Any refusal leaves source document, live owners, package, output bytes, relationships, content types and revision listings unchanged, with no partially created part or consumed public revision id visible. A partial custody-unit selection refuses before commit. Accepted result equals the edited input's part presence, identities, inventory, special bytes, unowned invalid and opaque bytes, and package graph. Rejected result equals the original input's. Both retire library-emitted custody markers when each part settles. Untouched completed imported markers remain byte-for-byte when their owner and part are untouched. When the current comparison adds custody to that part or edits the bound owner, imported completed markers are retired before emission. Both preserve prior revisions and untouched imported notes, specials, invalid definitions and opaque content. No new endnote topology. Endnote add or remove keeps the existing shell refusal, and a nonregression test covers text edit through compare, save, accept and reject.

## Listing and selection contract


### 4.1 Listing
`story_revisions` lists one entry per modeled revision element in the main document and related stories. It does not group entries by custody unit and does not expose the token. For the native pending fixture it returns three entries: body insertion id 1, note paragraph-mark insertion id 2 and note content insertion id 3. The public fields stay story, id, author, timestamp and kind. The count equals the number of revision elements. This preserves the existing listing and count contract.

### 4.2 Element selection
The public resolver computes a selected set of revision elements:

- `accept_all` and `reject_all`: every revision element.
- `accept_revisions_by_author` and `reject_revisions_by_author`: every element whose author equals the argument.
- `accept_revisions_in_date_range` and `reject_revisions_in_date_range`: every element whose timestamp is inside the inclusive range.
- `accept_revision_id` and `reject_revision_id`: every element whose current `w:id` equals the argument.
- The internal `accept_revision_ids` and `reject_revision_ids`: every element whose current `w:id` is in the set.

These are the actual callable semantics. Scope selection always compares the actual current ids, authors or timestamps. The token value does not constrain the comparison. A token argument may coincide with a current id of the same unit, a current id of an unrelated revision, or no current id at all. The resolver applies ordinary selection to every argument and then applies the partial-unit grouping rule in Section 4.3. Recognition never assumes token equality or non-equality with any current id.

### 4.3 Unit grouping and partial-unit refusal
Before commit, the resolver groups selected revision elements by custody unit using the persistent token, the body and note bookmark binding, the bound reference owner and the bound note owner. For each unit:

- If the selected set contains every revision element of the unit, the unit is fully resolved by the scope.
- If the selected set contains no element of the unit, the unit remains pending and is untouched.
- If the selected set contains some but not all elements of the unit, the resolver refuses atomically with a partial-unit error naming the story, token and owner. No element of the unit is resolved and no other revision is committed.

This rule applies to public id, author and date selectors and to the internal id-set path. `accept_all` and `reject_all` cannot be partial because they select every element. A unit with one revision element is trivially full when that element is selected. A non-custody revision is not grouped and is resolved by the ordinary scope rule.

### 4.4 Internal compare resolution
The compare-internal accept and reject path must not reuse the original shared id set after Word normalization. It rediscovers each custody unit from the markers and owners, reads the current revision ids of every element, and selects all of them. If it cannot discover every element, it refuses. This is internal and changes no public signature. The public element selectors remain as Section 4.2 states.

### 4.5 Proof cases
- Native pending fixture, token 7, body insertion id 1, note paragraph-mark insertion id 2, note content insertion id 3. `accept_revision_id(1)` selects the body element only, partial, refuse. `accept_revision_id(2)` selects the paragraph-mark element only, partial, refuse. `accept_revision_id(3)` selects the note content element only, partial, refuse. `accept_revision_id(7)` selects no element in this fixture, the unit stays pending, no error. `accept_revisions_by_author` selects all three when all three share the author and fully resolves. `accept_revisions_in_date_range` selects all three when all three share a timestamp in range and fully resolves. `accept_all` selects all three and fully resolves.
- Native pending deletion fixture, token 7, body deletion id 1, note paragraph-mark deletion id 2, note content deletion id 4, note marker a direct child of the note paragraph outside the deletion. Recognition is pending. `accept_revision_id(1)`, `(2)` and `(4)` each select one element and are partial, refuse. `accept_revision_id(7)` selects no element and leaves the unit pending. Author, date and all resolve every element when metadata matches.
- Token coincidence with a unit id: a normalized unit has token 7 and current ids 7, 8 and 9. `accept_revision_id(7)` selects one element of the unit, partial, refuse. It is not a no-op. If the same unit has current ids 7, 8 and 9 and id 7 also appears on an unrelated revision, selecting 7 selects the unit element and the unrelated revision. The unit is partial, so the whole resolution refuses and the unrelated revision is not committed.
- Token coincidence with an unrelated revision only: a normalized unit has token 7 and current ids 1, 2 and 3, and an unrelated revision has id 7. `accept_revision_id(7)` selects the unrelated revision, not the unit. The unit remains pending and the unrelated revision resolves normally. The token value does not make the unit pending or completed.
- Before Word normalization, when the shared id 7 appears on every element of the unit, `accept_revision_id(7)` selects every element and fully resolves. That is one possible coincidence, not a guarantee.
- Author or date mismatch inside a unit: body author A, note authors B. An author selector for A selects the body element only, partial, refuse. An author selector for B selects the note elements only, partial, refuse. `accept_all` selects all and fully resolves. A date range that covers only part of the unit refuses.
- Multi-reference owner: a note with two references has two body reference elements and one note content element plus one paragraph-mark element. Every body reference site must carry a revision wrapper while the note content wrapper is present. If only one site carries a wrapper while the note content wrapper is present, the unit is inconsistent and refuses. A selector that covers one reference element only is partial and refuses. Author, date or all covering every element fully resolves. The body bookmark is at the first reference site and the reference inventory lists both sites.
- Non-custody revision: a text edit with two revisions is not a custody unit. Selecting one id resolves that element and leaves the other, as the existing contract states.
- No custody marker: an ordinary bookmark with a similar name that fails the grammar is not a unit and is not grouped.

## Detailed discriminating countercases


### 20.1 Actual normalized fixture
- Pending: token 7 names, body insertion id 1, note paragraph-mark insertion id 2, note content insertion id 3, note marker parent `ins`, body marker parent `p`. Recognition is pending. Listing is three elements. Id selectors 1, 2 and 3 are partial and refuse. Token 7 selects no element in this fixture and leaves the unit pending. Author, date and all resolve every element when metadata matches. Library Accept keeps the normal definition and part and retires both markers at settlement. Library Reject removes the created part, relationship, content type, synthesized specials and normal definition.
- The note marker is inside the content insertion, so Word removes it with rejected content. The body marker is outside the insertion, so Word retains it. Those are observed Word bytes. The library resolver does not retain them: it retires both of its own markers at settlement.
- A valid normalized marker is never silently reclassified as an ordinary bookmark or an imported completed marker. It is pending while the reference and note content wrappers remain, and resolved only when those wrappers are gone or the reference and definition are gone.

### 20.2 Unrelated prior revision ids
- Token 7 is not compared to body id 1 or note ids 2 and 3. Pending detection reads the wrappers from the owners. An open unit with unrelated ids is preserved through an unrelated edit. The token remains identity. The allocator reserves token 7 and the bookmark ids so a new unit cannot reuse them.
- A later comparison that allocates a lower revision id does not change the open token. No id value is read as time.

### 20.3 Multi-reference owner
- All references to the same normal owner belong to one custody unit. The reference inventory lists every body site. The body marker is at the first site. The unit elements include every reference wrapper plus the note content and paragraph-mark wrappers.
- Every body reference site must carry a revision wrapper while the note content wrapper is present. If only some sites carry wrappers while the note content wrapper is present, the unit is inconsistent and refuses rather than being read as partially resolved.
- A selector covering one reference element only is partial and refuses. Author, date and all covering every element fully resolve. The multi-reference case is a design rule, not natively observed in the synthetic fixture.
- The controlled shared-reference native input with two direct references to one owner was refused by Word 16.114.1, while the one-reference baseline opened. This is a controlled negative for that representation, not a schema invalidity proof or a universal Word limitation. The library preserves the destination input's reference inventory and does not synthesize an extra reference, so a Word-admitted input cannot acquire a new shared reference through compare. Preserving an already-unreadable imported shared-reference input is retention, not generation.

### 20.4 Partial numeric, author and date selectors
- Numeric id: after normalization, ids 1, 2 and 3 each cover one element, so each is partial and refuses. Before normalization, if the shared id covers every element, the selector is full. A token argument may also coincide with a current id, in which case ordinary selection applies and partiality is decided from the selected elements.
- Author: if all elements share the author, the selector is full. If the body and note authors differ, an author selector covers a subset and refuses.
- Date: if all elements share a timestamp in the range, the selector is full. A range covering only part of the unit refuses.
- All: every element is selected, so every unit is fully resolved.
- Token as an id: in fixture 7 against ids 1, 2 and 3 it selects no element, so the unit remains pending and no error is raised. That is one example, not a universal rule. Token 7 against ids 7, 8 and 9 selects one unit element and refuses as partial. Token 7 against an unrelated revision id 7 selects that revision, not the unit. Scope selection always uses actual current ids.

### 20.5 Library destination outputs
- Library Accept All on the native fixture keeps reference 1, removes every revision, keeps the normal definition and part, keeps the relationship and content type, and retires both library-emitted markers at settlement.
- Library Reject All removes the reference, normal definition, part, relationship, content type and synthesized specials because the original input had no part, and retires both library-emitted markers at settlement. Word's observed Reject All retains the body marker and a separator-only part, but that is observed Word output, not the library postcondition.
- The predicate reads open units and retained content. A completed transaction leaves no markers and does not vote.

### 20.6 Completed and imported marker reopen
- After a library resolution settles a part, no library-emitted marker remains in it. Reopen shows the destination state: accept leaves the definition and part, reject leaves no part.
- An imported Word-resolved marker with a note counterpart and a live definition is a completed accept-state unit. An imported marker with an absent note counterpart, no reference and no definition is a completed reject-state unit. Both are preserved byte-for-byte when their owner and part are untouched, excluded from `U`, and retired when the library edits the bound owner or part or adds custody to that part.
- A malformed completed marker, such as a note counterpart present with a missing definition, refuses atomically rather than being reclassified as an ordinary bookmark.

### 20.7 Untouched invalid and opaque owners
- `Empty` and `Unknown` definitions are retained as unowned content. Opaque root content is retained. With no open unit, `U` is empty and `N = 0`, `R > 0` keeps the part. With open units, the predicate applies. The `N = 0`, `E = true`, `R > 0` case keeps the part because `R > 0` outranks `E`.
- If the edited input changes an invalid owner or its reference, the comparison refuses. If both inputs are unchanged, the bytes are preserved. No pruning, no reinterpretation and no blanket unsupported-input refusal.
- The N12 repair is preserved for both bit directions, `0/1` and `1/0`. A completed transaction's bits never decide presence, and an open transaction's bits vote only until the part settles.

### 20.8 Parser model and raw bytes
- The parser's public model is unchanged. The only parser identity changes are omitted type at `id <= 0` and explicit `normal` at `id <= 0`, both now normal. Empty and unknown non-empty read behavior is unchanged.
- Raw note types are recomputed on every open. They are never persisted, never added to a custom part and never exposed publicly.
- Untouched omitted and explicit normal owners at any id are normal. Untouched specials, invalid owners, opaque content and original unused notes are preserved. Previously valid untouched data is not refused.

### 20.9 Completed cycle with reopen
- Accept an open `1/0` deletion to absent. The predicate gives `N = 0`, `R = 0`, `E = true`, so the part is removed and its markers go with it. Reopen shows no part.
- Accept an open `0/1` addition. `N > 0` keeps the definition and part, and both markers are retired at settlement. Reopen shows the definition and part with no custody marker.
- Accept an open `1/1` removal toward separator-only. `N = 0`, `R = 0`, `E = false`, `base = 1`, so imported specials remain and both markers are retired at settlement.
- No prior open unit and no stale bit remain, so nothing forces the last part absent. Each transaction settles on its own.

### 20.10 Accept then edit the same retained normal note
- Accept an open `0/1` addition. The normal note remains and both markers are retired at settlement.
- Reopen and edit that note's text. No custody marker and no open unit exist, so the edit is an ordinary text edit. Stale provenance does not block it.

### 20.11 Imported Word-resolved markers
- A body marker with a note counterpart and a live definition, and a body marker with an absent counterpart, no reference and no definition, are completed imported units in a settled part. They are read from owner binding and wrapper absence, not from the token against current ids.
- Untouched, they are preserved byte-for-byte and excluded from `U`. When the current comparison edits the bound owner or part, including adding custody to that part, the completed marker is retired before new custody is emitted. Retiring removes the library-owned marker pair and applies ordinary part cleanup only when the predicate says the part is absent. It does not rewrite user content.

### 20.12 Token coincidence
- Token 7 with current ids 7, 8 and 9: `accept_revision_id(7)` selects one unit element, the unit is partial, and the resolution refuses. It is not a no-op.
- Token 7 with current ids 1, 2 and 3 and an unrelated revision id 7: `accept_revision_id(7)` selects the unrelated revision, not the unit. The unit stays pending and the unrelated revision resolves normally.
- Token 7 with current ids 1, 2 and 3 and no id 7: the selector selects nothing and leaves the unit pending. This is one example, not a universal theorem. Recognition never assumes token equality or non-equality with any current id.

### 20.13 Still-open creation lifetime and byte determinism
- The resolver distinguishes exactly two lifetimes from persisted bytes. An open lifetime exists while the part contains at least one pending unit, so every custody unit in that part, pending or retained tombstone, enters `U` and its bits vote. A completed lifetime exists when the part contains no pending unit, so library markers were retired and any remaining marker is imported and excluded.
- No current-versus-prior class exists. A unit emitted by the current comparison and the same unit reopened have the same names, bits, token, wrappers and ids. `N`, `R`, `base` and `E` are read from those bytes, so equivalent persisted bytes cannot require different outcomes because of missing in-memory history.
- Fresh compare, save, reopen, reject on an open `0/1` creation: `U` has the one unit, `N = 0`, `R = 0`, `base = 0`, so the part, synthesized specials and markers are removed. The outcome is identical before and after the save.
- Open `0/1` addition A, save and reopen, later `1/1` addition B, reject both with reopen between, in either order. Rejecting one leaves a retained tombstone and the other open unit, so the part stays. After both, `U` has both units, `N = 0`, `R = 0`, `base = 0` because A has `o = 0`, so the part and synthesized specials are removed. Rejecting B first and A first give the same final bytes.
- Selective resolve one unit, reopen, resolve the rest: the first resolution leaves a retained tombstone, reopen reads it as an open unit from its markers and wrapper absence, and the second resolution completes `U` and applies the same predicate. No in-memory record is needed.
- Three fully completed transactions `1/0`, `0/1`, `1/1`: each settles its own part, so its markers are retired and it does not enter a later `U`. The last `1/1` has `base = 1`, so the separator-only part remains. No stale `E` or `o = 0` survives to force absence.
- Imported Word-resolved markers live in a settled part, so they are excluded from `U` and preserved byte-for-byte when untouched. A comparison that adds custody to that part retires them first, so a library-produced open part never contains an imported marker. A foreign part that already mixes a pending unit with a no-wrapper marker is decoded as a retained tombstone, the only durable interpretation, and is outside the supported producer contract.
- Untouched invalid and opaque content is counted in `R`, so `N = 0` and `R > 0` keeps the part regardless of `E` or `base`. An open deletion with `e = 0` does not delete unowned content.
- Token magnitude is never read as chronology. `base` and `E` are derived from the bits of open units, not from token order or id value.

### 20.14 Imported completed marker followed by new custody versus a retained tombstone
- Case (1), a completed imported Word-resolved marker later followed by new pending custody. Before the later comparison the part is settled: it contains no pending unit and the imported marker has no bound wrapper. The comparison adds a new custody unit to that part. The producer retires every imported completed marker in that part before emitting any new marker. Published bytes therefore contain the new pending unit's markers and bound wrappers, and no imported marker. Recognition sees an open part whose only custody units are the new pending unit. The imported transaction's bits are gone and cannot vote.
- Case (2), a retained resolved tombstone in an actually still-open lifetime. The part contains at least one pending unit, meaning a bound owner still carries a revision wrapper. A resolved unit in that part keeps its markers with no wrappers. Persisted bytes therefore show at least one wrapper-bearing pending unit plus a no-wrapper marker bound to that part. Recognition reads the no-wrapper marker as a retained tombstone and its bits vote until the part settles.
- The durable discriminator is wrapper presence on a bound owner in the part. An open part has at least one pending unit. A settled part has none. The producer invariant makes a library-produced open part free of imported markers, because retirement precedes emission on every comparison entry point that adds custody. The token is identity, not chronology, and the allocator reserves completed tokens, so a new unit cannot reuse an imported token. No session memory and no numeric chronology are read.
- Reconciliation with Section 3 recognition: Section 3.5 defines the completed lifetime as a part with no pending unit, and Section 3.7 defines imported markers as settled-part metadata. Section 3.7's retirement sentence is the producer invariant, and Section 5 names every comparison entry point that must apply it. Accept, reject, save and reopen do not add custody and therefore do not need retirement.
- Reconciliation with untouched-byte preservation: a settled part's imported marker is preserved byte-for-byte when the comparison neither adds custody to that part nor edits the bound owner. When the comparison adds custody or edits the bound owner, the marker bytes are library-owned custody metadata, not user content, so retirement does not rewrite user content. Untouched imported notes, specials, invalid owners and opaque bytes remain.
- Honest limit: a foreign or corrupted part that already contains both a pending unit and a no-wrapper marker not retired by this library is outside the supported producer contract. The design decodes it as a retained tombstone because wrapper presence is the only durable discriminator. It does not claim to recover that foreign marker's transaction provenance. A malformed marker still refuses atomically.

### 20.15 Deletion-direction native placement
- Pending deletion: body deletion id 1, note paragraph-mark deletion id 2, note content deletion id 4, body marker id 0 outside the deletion as a direct child of `p`, note marker id 3 outside the deletion as a direct child of the note `p`, token 7 retained in both names. Recognition reads the wrappers from the bound owners and the current ids from those wrappers, so the non-consecutive ids and the retained token are irrelevant to recognition. The unit is pending because the body reference wrapper and the note content wrapper are both present.
- Accept All removes reference 1, normal owner 1 and the note marker, and retains the body marker, the special-only part, the relationship and the content type. Reject All retains reference 1, normal owner 1, the omitted type, the body marker and the note marker with no revisions. Those are observed Word bytes. The library destination states and settlement retirement are unchanged by this observation.
- The note marker sits outside the deletion here, unlike the insertion fixture where it sits inside the insertion. Placement is read owner-locally and is not assumed from direction. A note pair outside its bound owner or inside an arbitrary nested wrapper still refuses. This does not qualify selective resolution, multi-reference owners, schema validity, SDK validity or absent-part cleanup.
