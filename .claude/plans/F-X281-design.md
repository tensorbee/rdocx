## Approach

No new crate, module, file, trait, generic, or feature flag. `oxml-*` does not gain a dependency on `rdocx-*` or `rpptx-*`. `rdocx-layout` does not gain a dependency on `oxml-pdf`. `decode_image` and `DecodedImage` stay `pub(crate)` in `oxml-pdf/src/image.rs`. Cross-crate callers use one new public function implemented in that same file and publicly reexported with its result enum from `oxml-pdf/src/lib.rs`: `pub use image::{ImageDrawClass, classify_image_draw};`. Thus the callable paths are `oxml_pdf::classify_image_draw` and `oxml_pdf::ImageDrawClass`, while the `image` module, `decode_image` and `DecodedImage` remain private or `pub(crate)` as today.

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub enum ImageDrawClass {
    Drawn,
    UnsupportedFormat { kind: &'static str },
    CouldNotDecode,
    NotThisDecoder,
}

pub fn classify_image_draw(data: &[u8], content_type: &str) -> ImageDrawClass
```

`classify_image_draw` borrows both slices, returns a `Copy` value, and does not retain a buffer or mutate the caller's slices. The `Copy` return is not an allocation-free claim. `kind` is only `"emf"` or `"wmf"`. One private player in existing `oxml-pdf/src/image.rs` feeds both `classify_image_draw` and `decode_image`, so the class and the PDF raster cannot disagree. `rdocx` and `rpptx` already depend on `oxml-pdf` on the render path. `rdocx-layout` does not call this function and does not gain an `oxml-pdf` dependency.

PNG and JPEG classification calls the existing decode body and drops the raster. `decode_jpeg` copies the file bytes at `image.rs` 43. `decode_png` allocates `unfiltered` and `prev_row` at `image.rs` 140-141. A caller that classifies and then embeds runs that body twice. That is the existing decoder cost, not a cache and not a new pixel format. GIF, BMP, WebP, TIFF, and SVG are not sent through that decode. No zero-allocation measurement is claimed.

EMF classification uses the same size check and the same player as `decode_image`. The check runs before any RGBA `Vec` is allocated. An EMF that fails the check allocates no raster on either call. An EMF that passes and paints allocates the checked buffer. The classifier drops it. `decode_image` returns it for the XObject, which allocates that same bounded buffer again when both calls run.

Precedence is the first match.

1. A sniffed PNG or JPEG is `Drawn` when `decode_image` returns a raster, and `CouldNotDecode` when it does not. Probe failure, a zero width or height, a truncated chunk, and a failed inflate are `CouldNotDecode`. The content type does not override the sniff. PNG bytes with content type `image/emf` are not `UnsupportedFormat`.
2. A sniffed EMF is `Drawn` when the bounded subset paints, and otherwise `UnsupportedFormat` with kind `emf`.
3. A sniffed WMF is `UnsupportedFormat` with kind `wmf`. WMF is never `Drawn`.
4. Content type `image/emf`, `image/x-emf`, `image/wmf`, or `image/x-wmf`, when the sniff is not PNG, JPEG, GIF, BMP, WebP, TIFF, or SVG, is `UnsupportedFormat`. Kind is `emf` for the two emf types and `wmf` for the two wmf types. Empty bytes and unrecognized bytes take this outcome. `classify_image_draw(b"", "image/emf")` and `classify_image_draw(b"random", "image/emf")` are `UnsupportedFormat` with kind `emf`. The same bytes with `image/x-emf` are the same class. `b""` and `b"random"` with `image/wmf` or `image/x-wmf` are `UnsupportedFormat` with kind `wmf`.
5. GIF, BMP, WebP, TIFF, SVG, and every other payload that did not match items 1 through 4 are `NotThisDecoder`. Item 5 does not reclassify empty or unrecognized bytes that item 4 already classified. A sniffed GIF, BMP, WebP, TIFF, or SVG stays `NotThisDecoder` even when the content type is `image/emf` or `image/wmf`. `classify_image_draw(b"", "image/png")` and `classify_image_draw(b"random", "application/octet-stream")` are `NotThisDecoder`.

Both libraries follow this class. rpptx maps `Drawn` to `Ok(true)`, including a sniffed PNG or JPEG whose content type does not match the sniff. That mismatch is `Ok(false)` today at `lib.rs` 29064. `CouldNotDecode` is `Err("could not be decoded")`. `UnsupportedFormat` is the format `Err`. `NotThisDecoder` stays `Ok(false)`.

Two existing rpptx preview residuals stay `Ok(false)` and are not relabelled `CouldNotDecode`. A probed JPEG with `bit_depth != 8` or `channels != 3` (`lib.rs` 29072-29074) stays `Ok(false)`, because `decode_jpeg` (`image.rs` 36-49) returns `Some` for any probed JPEG and does not reject the channel count. A PNG that decodes but does not change the preview pixels (`lib.rs` 29078-29124) stays `Ok(false)`. rdocx may still embed those rasters. No new public method splits them.

A boolean helper is not the contract. It cannot separate an unsupported EMF, a corrupt PNG, and a GIF that must stay on the old `Ok(false)` path.

### A281-1 EMF, raster subset

Implement the player in existing `oxml-pdf/src/image.rs` and call it from `decode_image` when `classify_image_draw` would return `Drawn` for EMF. `probe` in existing `oxml-media/src/lib.rs` gains `Some(ImageInfo)` for EMF. It keeps today's `Some` results for GIF, BMP, and WebP (`lib.rs` 325-332). It stays `None` for WMF, TIFF, and SVG. Width-only `add_picture` for GIF, BMP, and WebP keeps today's result. The EMF pixel size is the inclusive bounds: `width_px = right - left + 1` and `height_px = bottom - top + 1`, when that difference is positive and fits in `u32`. The issue header `red_emf(200, 100)` stores bounds `0, 0, 199, 99`, so the probe result is 200 by 100. No division is involved. Width-only `add_picture` then keeps that aspect, and a 3 inch width is 1.5 inch tall. The 2700 red-pixel gate stays the observation. This pass did not render it.

If the bounds are not a positive inclusive rectangle, the fallback uses the frame. `width_hmm = rclFrame.right - rclFrame.left` and `height_hmm = rclFrame.bottom - rclFrame.top`, as `i64`, with no `+1`. The `+1` belongs only to inclusive pixel bounds. Pixels are `(width_hmm * 96) / 2540` and `(height_hmm * 96) / 2540`, integer division truncating toward zero. A non-positive result stays `None`, and `add_picture` still raises `UnavailablePictureDimensions` at 11702. The issue script stores frame `0, 0, 5290, 2645` for `red_emf(200, 100)` (`issue-436-body.md` 36-47). On that frame the arithmetic is 199 by 99. That figure is integer arithmetic, not a rendered measurement. `szlDevice` and `szlMillimeters` are the reference device, not the picture pixel size. Using 1024 by 768 for this header would change the aspect from 2:1 to 4:3, so they are not `width_px` or `height_px`.

The PDF XObject raster uses an integer scale. `longest` is the bounds long side. `scale = (1024 / longest).clamp(1, 8)` by truncating division. Output pixels are bounds pixels times `scale`. There is no fractional pixel. Before any raster `Vec` is allocated, the player computes `out_w = u64::from(width_px) * u64::from(scale)` and `out_h = u64::from(height_px) * u64::from(scale)`, then `bytes = out_w.checked_mul(out_h).and_then(|pixels| pixels.checked_mul(4))`. The allocation proceeds only when `bytes` is `Some(n)`, `n > 0`, and `n <= 64 * 1024 * 1024`. Overflow and a larger product refuse. The same ceiling is applied to a `STRETCHDIBITS` source buffer before that buffer is allocated. A refused record does not draw and does not allocate. If nothing draws, the class is `UnsupportedFormat` and `decode_image` returns `None`. This ceiling lives in the shared player. `rpptx` `MAX_RENDER_PREVIEW_DECODED_BYTES` at `lib.rs` 29130 stays on the existing PNG and JPEG preview path and is not this check. PNG and JPEG `decode_image` keep today's allocations and today's refusal behavior. The new ceiling is not added to them.

The issue header stays inside the ceiling. Width 200 and height 100 give `longest` 200 and `scale` 5, then 1000 by 500 pixels and 2,000,000 bytes. The page gates remain at least 1200 red pixels for the 2 by 1 inch page and at least 2700 for the 3 by 1.5 inch slide. Those counts are page pixels. Bounds `0, 0, 100000, 100000` are width 100001 and height 100001, `scale` 1, and a product above the ceiling. That input is `UnsupportedFormat`, `decode_image` returns `None`, and no RGBA buffer is allocated. `probe` may still return `Some` for that readable header, because probe stores dimensions and does not allocate RGBA, so width-only `add_picture` does not raise `UnavailablePictureDimensions` for it. The refusal is the draw. This pass did not allocate that buffer. Sample documents are built from PNG helpers in `generate_all_samples.rs` and do not take the EMF path.

The subset that may set a drawn flag: window and viewport origin and extent, map mode, world transform, save and restore, stock and created solid pens and solid brushes, polygons, polylines, and Beziers in 16-bit and 32-bit forms, rectangles, rounded rectangles, ellipses, path brackets, and `EMR_STRETCHDIBITS` at 1, 4, 8, 24, and 32 bits. The issue script's records are inside that subset: `EMR_CREATEBRUSHINDIRECT` 39, `EMR_SELECTOBJECT` 37, `EMR_RECTANGLE` 43, `EMR_EOF` 14.

These do not draw and do not set the drawn flag: text, clipping, `BITBLT`, `STRETCHBLT`, `ALPHABLEND`, dashed pens, hatched brushes, EMF+ comments, and every WMF. If the flag stays false, `decode_image` returns `None`. Output is an RGBA raster, then a PDF image XObject. This is not a vector claim, including in PDF.

The issue's 2 by 1 inch page at 30 dpi still has at least 1200 red pixels (`r > 150`, `g < 80`, `b < 80`). The 3 by 1.5 inch slide has at least 2700. Those thresholds are the local gate. They are page-pixel counts, not the XObject's internal pixel count.

rdocx diagnostics cannot be born only in the PDF writer, because the public lists are copied from layout before encode. `PositionedElement::Image` carries `media_id: MediaId`, and `MediaId::from_bytes` is an FNV-1a hash of the bytes (`oxml-layout/src/output.rs` 75-85 and 370-375).
